# KoLo セキュリティ概要

English: [Security Overview](/security/SECURITY_OVERVIEW)

このページは、自社ホストの KoLo についてセキュリティレビューで問われる事項に答えます。各項目は仕組みと、確認に使えるコマンドを示します。対象バージョン: KoLo 2.0.0 以降（`kolo --version` で確認）。

## 1. 配置モデル

- KoLo は自社ホスト型のソフトウェアです。識別名ごとに 1 つのゲートウェイプロセスが、評価者のマシンまたはサーバー上で OS のサービス管理（systemd ユーザーサービス、launchd エージェント、Windows タスク スケジューラ）の下で動作します。評価構成に KoLo 側が運用するクラウド構成要素はありません。
- すべての状態は 1 つのディレクトリ `KOLO_HOME`（Linux / macOS は `~/.kolo`、Windows は `%LOCALAPPDATA%\KoLo`）に置かれます。それ以外に書き込むのはインストール先のプログラムファイルだけです。
- クライアント（ターミナル、Web UI、ペアリングした端末、メッセージングチャネル）は WebSocket と HTTP でゲートウェイに接続します。ゲートウェイは、設定されたモデルプロバイダーと、運用者が有効化したチャネルに対してのみ外向き通信を行います。

## 2. マシンの外に出るデータ

| 通信 | 宛先 | 既定 | 無効化の方法 |
|---|---|---|---|
| モデルへのリクエスト（プロンプト、ツール結果、応答） | 運用者が設定したプロバイダー（標準プロファイルは国内ホストの OpenAI 互換サービス、またはローカルのモデルサーバー） | プロバイダー設定後のみ | `kolo init` で `local` プロファイルを選ぶ |
| メッセージングチャネル | 各チャネル事業者の API（LINE、Telegram など） | 無効 | チャネルを有効化しない |
| 更新確認 | パッケージレジストリ（バージョン情報のみ） | npm インストールではゲートウェイ起動時 | `kolo.json` で `update.checkOnStart: false` |
| mDNS/Bonjour の告知 | ローカルネットワークへのゲートウェイ名のブロードキャスト | minimal | `gateway.discovery.mdns.mode: "off"` |
| インストーラーのダウンロード | github.com（リリースバンドルと SHA256SUMS.txt） | インストール時のみ | `--bundle` によるオフラインインストール |

テレメトリー、アナリティクス、クラッシュレポート、利用統計は送信しません。ゲートウェイは実行時に KoLo や提供元へ接続しません。詳細は [プライバシー](/ja/security/privacy) を参照してください。

## 3. ネットワーク公開範囲と接続ポリシー

- 既定の待ち受けはループバック（`127.0.0.1` / `::1`）です。リモートアクセスには `gateway.bind` の明示設定（`lan`、`tailnet`、`custom`）と、すべての接続でのトークンが必要です。
- `/api/*` 配下のすべての HTTP ルートと、すべての WebSocket メソッドは資格情報を要求します。認証なしで応答するのは `GET /health` と `GET /api/health` だけで、返すのは状態・バージョン・稼働時間のみです。詳細な準備状況は資格情報が必要です。
- 資格情報の試行は送信元アドレスごとにレート制限されます（毎分 20 回）。
- API は OpenAPI 3.1 文書（`GET /doc`、資格情報が必要）で記述され、各操作が最小スコープを宣言しています。

## 4. 認証と認可

- ゲートウェイシークレット: `kolo init` が生成するランダムな 256 ビットのトークン。`KOLO_HOME/secrets/gateway.token` にファイル権限 0600 で保存され、コマンドライン引数には渡されません。
- 端末のペアリング: スコープ付き（`observe` < `attach` < `admin` < `owner`）で有効期限が数分の 1 回限りの招待コード。端末はサーバーのノンスに対する Ed25519 鍵の所有を証明し、短命のアクセストークンとローテーションするリフレッシュトークンを受け取ります。失効済みリフレッシュトークンの再利用は、そのトークン系列全体を取り消します。端末はいつでも取り消せます（`kolo pair revoke`）。一定期間（既定 90 日）後に再同意が必要です。
- セッション許可リストにより、資格情報を特定のセッションやエージェントに限定できます。
- エージェントのツール実行は、運用者の実行承認（`kolo approvals`）とサンドボックス設定の下で行われます。

確認: `kolo pair list`、`kolo pair invite --scope observe` の後に管理ルートへアクセス（403 を期待）。

## 5. シークレット

- プロバイダーの鍵やチャネルのトークンは、`KOLO_HOME` 配下の認証プロファイルストアと暗号化シークレットストアに保存されます（`kolo secrets list` でバックエンドを表示）。設定ファイルはシークレットを名前で参照し、`kolo secrets migrate` で `kolo.json` から平文の値を移動できます。
- シークレットはどのコマンドも表示せず、コマンドライン引数としては受け付けず（`--stdin` または環境変数を使用）、ログではマスクされます。
- 他ツールの資格情報ファイルからの取り込みは明示的な操作（`kolo doctor --verbose`）でのみ行われ、自動では行われません。

## 6. 監査ログ

- すべての認証、ペアリング、セッション接続／切断、管理操作、ツール実行は、`KOLO_HOME/audit/` 配下のハッシュチェーン付き監査ログに追記されます（月ごとに 1 ファイル。各エントリは直前エントリのハッシュを含みます）。
- `kolo audit verify` はチェーンを再計算して最初の断絶を報告し、`kolo audit tail` は直近のエントリを表示します。ゲートウェイからは追記のみです。改ざんは検出できますが、ファイルを追記専用ストレージに転送しない限り防止はできません。

## 7. 起動時の整合性ゲート

- `kolo integrity init` は、インストールの基本ファイル（エージェントへの指示、ポリシー）の SHA-256 ダイジェストを記録します。起動のたびにゲートウェイが再検証し、`enforce` モードでは不一致があると起動を拒否（終了コード 3）、`warn` モードでは起動したうえで `/health` に `integrity: warn` を報告します。
- 確認: 登録済みファイルを変更して再起動し、`kolo service logs` で拒否を確認。

## 8. 保存データと保持期間

| データ | 場所 | 保持 |
|---|---|---|
| 設定 | `KOLO_HOME/kolo.json` | 変更または削除まで |
| ゲートウェイトークン、シークレット、端末の資格情報（ハッシュのみ） | `KOLO_HOME/secrets/`（0600） | 取り消しまたは削除まで |
| セッションと会話記録 | `KOLO_HOME/agents/<id>/sessions/` | 削除するまで（`kolo sessions`、または完全削除）。自動アップロードなし |
| エージェントの作業領域とメモリ | `KOLO_HOME/workspace/` | 削除まで |
| ログ | `KOLO_HOME/logs/` | 日次ローテーション。自由に削除可 |
| 監査チェーン | `KOLO_HOME/audit/` | 月次ファイル。ポリシーに従って保管 |
| サポートバンドル | `KOLO_HOME/support/` | `kolo support` 実行時のみ生成。マスク済み |

ファイルはサービスユーザーの OS 権限で保護されます。ホストのフルディスク暗号化を推奨します。KoLo はシークレットストア以外に独自のディスク暗号化を追加しません。

## 9. 完全削除

```bash
kolo service uninstall            # OS サービスを停止して削除
kolo uninstall --all --yes        # KOLO_HOME（設定、シークレット、セッション、監査、ログ）と作業領域を削除
rm -rf <インストール先>            # ~/.local/share/kolo と ~/.local/bin/kolo、または %LOCALAPPDATA%\KoLo
```

`kolo uninstall --all --yes --dry-run` で削除対象を事前に確認できます。これらのパス以外には何も残りません。ペアリング済み端末が持つのは削除されたゲートウェイが発行したトークンだけで、無効になります。

## 10. ソフトウェアサプライチェーン

- リリースバンドルは `SHA256SUMS.txt` とともに公開され、インストーラーはダイジェストが一致しないダウンロードを拒否します。
- `pnpm release:check` はエントリポイントが参照するすべてのファイルがパッケージに含まれることを検証し、`pnpm pack:check` は CI でパッケージを空のディレクトリにインストールして実行します。
- 依存関係は `pnpm-lock.yaml` で固定され、CI はソースにシークレットスキャナーを実行します。
- リリース: すべてのリリースに SHA-256 チェックサム、CycloneDX SBOM、ビルド来歴（provenance）証明を添付。macOS/Windows バイナリのコード署名は計画中（公開ロードマップ参照）。

## 11. 脆弱性対応

security@kodasoken.com へ報告してください。3 営業日以内に受領連絡、10 営業日以内にトリアージ、確認された高・緊急の問題は 30 日以内に修正、報告から最長 90 日で協調開示します。詳細はリポジトリの `SECURITY.md` を参照してください。
